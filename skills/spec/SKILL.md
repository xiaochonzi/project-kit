# Spec

## Overview

把已接受 Proposal 转化为可验证、可冻结的业务契约，填写既有的 `docs/changes/CR-###-<slug>/spec.md`。本技能回答“系统必须表现成什么样”，不回答“代码具体怎么写”。

**开始前宣布：**“我正在使用 spec 技能设计业务契约。”

## The Iron Law

```
NO PLAN OR IMPLEMENTATION DETAILS IN AN UNAPPROVED BUSINESS SPEC
```

Spec 有歧义、矛盾或阻断性未决问题时必须继续澄清。不得把业务决定留给 Plan 或实施阶段猜测。

## Spec 的定位与细节度

Spec 是三件套中**唯一冻结业务契约**的文档。它的读者是任意 AI 工具，读完必须能：

1. 写出验收测试，且不存在第二种合理解释；
2. 不发明任何 Spec 之外的业务行为。

**细节度双向判据**：

- **下限**：消除歧义——不参与原始讨论的人仅凭本文能写出测试，且无第二种合理解释。
- **上限**：不越界到 Plan 的职责——只写对外契约，不写内部实现符号。

**对外契约 vs 内部实现的判定表**：

| 允许写（对外业务契约） | 禁止写（内部实现） |
| --- | --- |
| API 输入输出字段 + 语义 + 错误码 | 类名、包路径、函数名 |
| 幂等键、状态机、数据权威（谁拥有这个事实） | 内部调用链、技术栈、事务实现 |
| wire format 字段级定义 | 文件路径 |
| 数据权威表（每个事实的唯一权威） | DTO/VO 类名 |
| 业务流程图（参与者=业务角色） | 技术调用链图（参与者=类名） |

**规范关键词**：全文使用 `必须` / `不得` / `应该` / `服务端权威`（RFC 2119 风格），禁止“适当处理”“体验良好”“正常工作”等不可验证描述。

**一条信息只写一次**：Spec 定义业务契约，Plan 只引用编号（REQ/BR/AC），不复制正文。

## Required Inputs

- [ ] `proposal.md` 存在且 `status: accepted`
- [ ] 同目录 `spec.md` 存在且 `status: draft`
- [ ] 已读取项目规则、`docs/blueprint.md`（如有）、相关已批准 Spec 和当前代码现实
- [ ] 用户目标属于一个可独立验收的 change；多个独立系统先返回 `change` 拆分

若 Spec 已 approved，不重写，直接交接 `plan`。若 Proposal 未 accepted，返回 `change`。

## Process

### Step 1：加载上下文并探查代码现实

```bash
node scripts/project-docs.cjs context spec --target <CR-###> --root <项目根>
```

完整读取 Proposal、draft Spec、项目规则、Blueprint 和相关契约。然后搜索真实代码和测试，形成基线：当前行为是什么、差距是什么、现有集成点和约束是什么。先探查，再提问题；不得根据 Proposal 标题臆测系统现状。

### Step 2：逐项澄清

一次只讨论一个主题，按实际缺口从以下视角推进：

1. **现状**：谁遇到什么问题，当前系统具体怎样表现。
2. **最小结果**：解决核心问题所需的最小业务能力。
3. **边界**：明确做什么、不做什么、哪些现有行为保持不变。
4. **失败分析**：无效输入、空值、极值、重复、越权、乱序和部分失败会怎样。
5. **验收**：怎样用可观察结果判断 PASS/FAIL。

存在多个合理业务方案时，给出 2–3 个方案、取舍和推荐，等待用户选择。不要把所有问题一次抛给用户。

### Step 3：建立稳定契约

每项需求使用稳定编号：

```markdown
### REQ-01：<需求名称>

- Current：<当前行为>
- Trigger：<角色、前置条件与触发>
- Target：<目标行为与结果>
- Business Rules：BR-01、BR-02
- Acceptance：AC-01、AC-02
```

- `REQ-##`：可独立理解的业务需求。
- `BR-##`：业务规则或始终成立的不变量；条件较多时使用决策表，不用散文。
- `AC-##`：能够得到 PASS/FAIL 的验收标准，包含具体输入、动作和结果。

编号一经用户批准不得重新排序。删除需求时说明废弃原因，不把其他编号整体前移。编号不得有字母后缀变体（`AC-09a` 不合法，应重编号为下一个整数）。

### Step 4：完成必填核心

以下内容全部必填：

- 术语与业务对象：定义可能影响理解的名称、状态和对象；无新增含义时说明沿用的现有定义；每个 ID 定义到唯一无歧义（如“`<对外 ID>` = `<具体数据表>.<字段>`”，不允许“`<某个 ID>` 到底指哪个 ID”的歧义）
- **数据权威表**：用一个表格列出每个业务事实的唯一权威（当前用户/租户是谁、内容是否属于任务、任务总体进度等），消除“该信谁”的猜测
- 问题与依据：代码现实、用户问题和触发原因
- 目标：一个具体、可观察的结果
- 用户流程：角色、前置条件、触发、主流程、结果；覆盖每个分支（正常+异常），参与者只能是业务角色，禁止类名
- 范围：包含、不包含、保持不变
- 输入与输出：业务输入、输出和对外契约；写到字段级 + 错误码 + 幂等键，覆盖成功/失败/边界三种响应变体，不只 happy path
- 业务规则：全部 REQ 和 BR，BR 用决策表表达，不用散文
- 失败与边界情况：失败时的明确行为，每条给“必须行为”（情况 → 必须行为 的决策表）
- 禁止事项：系统明确不得发生什么
- 验收标准：全部 AC，每条含具体输入、动作、可观察结果，覆盖三种结果变体
- 未决问题：批准前必须精确写为“无”

**业务流程图 vs 技术调用链**：Spec 画业务流程图（参与者=用户/前端/后端/领域系统，每节点标注触发条件、前置条件、结果、失败分支）；技术调用链（参与者=类名）属于 Plan，不得混入 Spec。

### Step 5：按适用性完成条件设计

逐项判断是否适用；适用则写清契约，不适用则在相关章节写“本变更不涉及：原因”，不得留空：

| 类别 | 必须回答的问题 |
|---|---|
| API / 事件 | 输入、输出、错误、顺序和兼容行为是什么 |
| 数据与状态 | 概念、所有权、状态迁移、创建/更新/删除时机是什么 |
| 权限与安全 | 谁可以看或做什么，拒绝时怎样表现 |
| 重复与并发 | 重复请求、幂等、并发冲突如何处理 |
| 超时与部分失败 | 重试、回滚、补偿和可见结果是什么 |
| 兼容与迁移 | 旧数据、旧客户端、回滚和过渡期如何处理 |
| 非功能要求 | 性能、容量、审计、可观测性是否有可测阈值 |
| UI 状态 | loading、empty、error、disabled 和权限态如何表现 |

涉及新数据模型时，可在业务关系确认后执行 `new diagrams --change <CR-###>`，把模型关系和操作时机写入同一 change 目录的可选 `diagrams.md`。

### Step 6：边界与禁止事项审计

对每个 REQ 检查：空值、无效值、边界值、重复、乱序、越权、并发、部分失败、兼容和恢复。只记录适用项；每个被排除的相邻能力写入“不包含”并说明原因。禁止使用“正常工作”“适当处理”“体验良好”等不可验证描述。

### Step 7：自审

1. 扫描模板标记、TBD、TODO、空章节。
2. 检查目标、流程、规则、失败行为和 AC 是否互相一致。
3. 检查每个 REQ 是否关联 BR 和 AC，每个 AC 是否可独立 PASS/FAIL。
4. 检查是否混入文件、函数、代码或任务级实现细节。
5. **反向扫描越界**：全文出现任何类名、包名、文件路径（如 `<类名>`、`<包路径>`）即为越界，删除或改为业务角色表述。
6. 检查是否包含多个应拆分的独立系统或未经请求的能力。
7. 扫描“按之前讨论”“同上”“相关逻辑”“适当处理”“根据实际情况”“后续再定”等模糊引用；把它们改成明确规则、示例或边界。
8. 检查术语、输入输出、状态名称和失败结果是否只有一种合理解释；必要时增加决策表或具体示例。
9. 检查输入输出是否覆盖成功、失败、边界三种响应变体，不只 happy path；是否写全数据权威表。
10. 检查编号是否有字母后缀变体（如 AC 后接字母的编号，应重编号为下一个整数）。
11. 检查是否复制了 Plan 范畴的实现细节（类名/调用链/技术栈）。

发现问题直接修正；需要产品决定时停止并只问当前最关键的一个问题。

### Step 8：用户批准并冻结

完整展示 Spec 摘要、范围、关键规则、失败行为和 AC。用户明确批准后：

```bash
node scripts/project-docs.cjs transition CR-### --to approved --kind spec --root <项目根>
```

脚本会拒绝占位符、缺少 REQ/BR/AC、空核心章节、字母后缀编号或未决问题不为“无”的 Spec，并把状态更新为 approved。

## 校验清单

- [ ] Proposal accepted，Spec 原始状态为 draft
- [ ] 代码现实已探查，Current 不是猜测
- [ ] 术语与业务对象、数据权威表、必填核心全部完成，条件设计均已填写或说明不适用
- [ ] 输入输出覆盖成功/失败/边界三种响应变体，不只 happy path
- [ ] 全文无类名/包名/文件路径（对外契约字段除外），无“适当处理”类模糊表述
- [ ] 业务流程图用业务角色，未混入技术调用链
- [ ] 每个 REQ 有规则和验收映射
- [ ] 无阻断问题、占位符、歧义和实现任务
- [ ] 编号无字母后缀变体
- [ ] 用户明确批准，状态迁移成功

## 脚本/AI 分工

| 脚本 | AI |
|---|---|
| `context spec` 输出上下文路径 | 探查现实、澄清业务、设计契约 |
| `transition` 校验结构、编号、占位符并迁移状态 | 判断适用性、解决歧义、请求用户批准 |
| `validate` 检查结构与状态 | 不写实现计划，不替用户做产品决定 |

## 停止条件

- Proposal 未 accepted 或范围发生变化 → 返回 `change`。
- 需求包含多个独立系统 → 返回 `change` 拆分。
- 需要改变 Blueprint 的系统边界但尚未确认 → 暂停并处理 Blueprint。
- 存在业务矛盾、两种合理解释或阻断性未决问题 → 询问用户。
- 发现需要文件级或技术实现决定 → 留给 `plan`，不得写入业务契约。

## Handoff Rule

Spec approved（需要时 `diagrams.md` 已确认）→ `plan`。本技能不写 Plan、不执行代码。

## Common Rationalizations

| 借口 | 现实 |
|---|---|
| “Plan 阶段可以自己补边界” | 未写入 Spec 的行为无法追踪，也无法稳定验收 |
| “多写几段说明就够了” | 完备性来自稳定 ID、明确规则和 PASS/FAIL 契约 |
| “先 approved，问题放 Plan 决定” | Plan 只能选择技术实现，不能发明业务行为 |
| “所有条件类别都写不适用最快” | 适用性必须根据真实业务与代码判断，不能机械跳过 |
| “把类名写进去更精确” | 类名是内部实现，写进 Spec 会让执行者死磕过时细节 |
