# Spec

## Overview

把 accepted Proposal 编译为可以冻结的业务契约，完整写入既有 `docs/changes/CR-###-<slug>/spec.md`。Spec 回答“系统必须表现成什么样”，使没有原始对话上下文的 AI 能写出一致的验收测试，且不需要发明业务行为。

Spec 不规定内部类、文件、函数、调用链或任务顺序；这些属于 Plan。

**开始前宣布：**“我正在使用 spec 技能设计业务契约。”

## Iron Law

```text
NO APPROVAL WHILE A SECOND REASONABLE INTERPRETATION EXISTS
```

只要角色、输入、权威、状态、失败结果或验收仍有两种合理解释，就必须继续澄清。不能把业务决定留给 Plan 或执行阶段。

## Required Inputs

- [ ] `proposal.md` 存在且 `status: accepted`
- [ ] `spec.md` 存在且 `status: draft`，正文可以只有最小骨架
- [ ] 已读取 Proposal 的 EVD、DEC、包含和不包含
- [ ] 已读取项目规则、Blueprint、相关 approved Spec 和当前系统行为
- [ ] 当前 Change 是一个可独立验收的业务目标

Proposal 未 accepted → 返回 `change`。Spec 已 approved → 不重写，交接 `plan`。

## Contract Boundary

| Spec 可以定义 | Spec 不得定义 |
| --- | --- |
| 角色、触发、前置条件、业务流程 | 内部类名、包名、函数名 |
| 对外 API / 事件字段、语义、错误 | 文件路径和代码修改步骤 |
| 数据权威、业务状态和迁移规则 | 内部调用链和模块实现 |
| 权限、幂等、并发、兼容行为 | DTO/VO 名称和任务拆分 |
| UI 可观察状态和验收结果 | 技术栈选择和测试文件安排 |

若 API、事件、字段、路径本身是对外契约，可以精确定义；但不得指定内部代码组织。

全文优先使用“必须 / 不得 / 应该 / 服务端权威”等规范词。禁止“正常工作”“适当处理”“体验良好”。

## Process

### Step 1：加载上下文与探查当前行为

```bash
node scripts/project-docs.cjs context spec --target <CR-###> --root <项目根>
```

先探查真实系统、测试和既有契约，再写 Current。探查目标是确认：

- 当前用户可观察行为
- 已存在的业务对象、状态和外部契约
- 当前事实由谁权威维护
- Proposal 与现实是否冲突
- 哪些分支和失败行为尚未决定

内部文件和 Symbol 可用于探查，但不复制进 Spec。若 Proposal 范围与现实冲突，停止并返回 `change`。

### Step 2：逐项消除产品歧义

一次只处理一个主题：

1. 角色、场景、触发和前置条件
2. 最小目标结果
3. 包含、不包含和保持不变
4. 数据权威和状态变化
5. 成功、失败、边界、重复、乱序、越权和恢复
6. 可观察的 PASS / FAIL 标准

存在多个合理方案时，给出 2–3 个选项、取舍和推荐，等待用户选择。选择完成后把结论写入契约，不保留“建议采用”式未冻结表达。

### Step 3：选择适用的契约块

所有 Spec 都必须完成核心契约；其他契约块按需求适用性生成。不要把任何需求强行塞入固定示例。

#### 核心契约

- 术语与业务对象
- 数据权威表
- 问题与依据
- 目标
- 用户流程
- 范围
- 输入与输出
- 业务规则
- 失败与边界情况
- 禁止事项
- 验收标准
- 未决问题

#### 条件契约块

| 契约块 | 适用时必须明确 |
| --- | --- |
| 状态 | 状态集合、合法迁移、非法迁移、终态 |
| 决策 | 条件组合与唯一结果的决策表 |
| 字段 | 名称、类型、必填、语义、权威来源、修改权限 |
| API / 事件 | 方向、产生方、承载位置、顺序、成功/失败响应 |
| Action | 稳定名称、允许组件、对应业务事件、校验行为 |
| 权限 | 谁能看/做什么，拒绝时的可观察结果 |
| 幂等并发 | key、重复结果、竞争冲突和恢复 |
| 兼容迁移 | 旧数据、旧客户端、过渡期和回滚 |
| UI 状态 | loading、empty、error、disabled、权限和终态 |
| 非功能 | 可测的性能、容量、审计和可观测阈值 |

适用则写清规范；不适用则在相关章节写明原因。不得机械写“全部不适用”。

### Step 4：从空正文编写完整 Spec

#### 术语与业务对象

每个名称只能有一种含义。每个对外 ID 必须定义其业务对象；不能留下“某个 ID 到底是哪种 ID”的歧义。

#### 数据权威表

用表格回答每个业务事实“应该信谁”：

```markdown
| 业务事实 | 唯一权威 | 非权威来源不得做什么 |
| --- | --- | --- |
```

UI 状态、缓存、对话状态和持久业务事实必须明确区分。

#### 用户流程

覆盖主流程和适用的失败分支。参与者使用用户、客户端、服务端、领域系统等业务角色，不使用内部类名。每个步骤写清触发、前置条件、结果和失败去向。

#### 输入与输出

写到字段级，覆盖成功、业务失败和边界响应。明确：

- 字段类型、必填和语义
- 字段由谁产生、谁可以修改
- 幂等键和关联 ID
- 错误或拒绝结果
- 顺序和兼容要求

JSON 或表格示例必须标记：

- `Normative`：结构和语义属于契约
- `Illustrative`：示例值不是固定业务值

#### 稳定契约编号

```markdown
### REQ-01：<需求名称>

- Current：<当前可观察行为>
- Trigger：<角色、前置条件、触发>
- Target：<唯一目标行为>
- Business Rules：BR-01、BR-02
- Acceptance：AC-01、AC-02
```

- `REQ-##`：可独立理解的需求
- `BR-##`：始终成立的规则或不变量
- `AC-##`：具体输入、动作、可观察结果组成的 PASS / FAIL 标准

编号批准后不得重排。禁止字母后缀（例如 `AC-09a`）；新增标准使用下一个整数。

### Step 5：建立单一事实来源

一个事实只定义一次：

- 稳定名称集中在术语或 Registry
- 状态迁移集中在状态表
- Event / Action / Field 集中在各自 Registry
- 流程章节只引用稳定名称，不重新发明语义
- AC 引用 REQ / BR，不复制整段契约

同一个字段、事件、Action 或状态在不同章节出现不一致时，Spec 不得 approved。

### Step 6：边界攻击

对每个 REQ 检查适用项：

- 空值、无效值、边界值
- 重复、并发、乱序、超时
- 越权、跨租户、篡改
- 部分失败、重试、回滚、恢复
- 旧数据、旧客户端、历史状态
- UI 恢复和重复消费

使用“情况 → 必须行为”决策表，不使用模糊散文。

### Step 7：文档自检

重新只读落盘 Spec，不依赖原始对话，逐项确认：

1. 能否仅凭 Spec 写出每条 AC 的测试输入、动作和预期？
2. 每个事实是否只有一个权威来源？
3. 每个状态、字段、Event、Action 是否只有一个稳定名称和语义？
4. 是否存在“建议 / 或者 / 暂时 / 等价实现 / 后续再定”等隐藏选择？
5. 成功、失败和边界响应是否都已定义？
6. 示例是否说明 Normative / Illustrative？
7. 是否混入内部文件、类、函数、调用链或任务？
8. 是否有事实只存在于原始对话或外部材料？
9. Proposal 的全部 DEC 是否被遵守且没有被重新选择？
10. 是否仍能构造第二种合理业务解释？

发现问题直接修正。需要产品决定时停止，只问当前最关键的一个问题。

### Step 8：用户批准并冻结

展示目标、范围、数据权威、关键 Registry、失败行为和全部 AC。用户明确批准后：

```bash
node scripts/project-docs.cjs transition CR-### --to approved --kind spec --root <项目根>
```

CLI 只检查章节、编号、占位符、契约关联和未决问题；业务真实性和唯一解释由文档作者与用户负责。

## Quality Checklist

- [ ] Proposal accepted，Spec 原状态为 draft
- [ ] Current 来自真实探查，不是猜测
- [ ] 核心契约全部完成，条件契约块已展开或说明不适用
- [ ] 数据权威表覆盖适用业务事实
- [ ] 输入输出覆盖成功、业务失败和边界响应
- [ ] 每个 REQ 关联 BR 与 AC，每个 AC 可独立 PASS / FAIL
- [ ] Registry 中的名称、字段、方向和权威无冲突
- [ ] 无文件、类、函数、技术调用链或任务级实现细节
- [ ] 无原始对话依赖、未冻结选择、占位符和字母后缀编号
- [ ] 仅凭落盘 Spec 不存在第二种合理业务解释
- [ ] 用户明确批准并成功迁移状态

## Script / Author Responsibility

| CLI | 文档作者 |
| --- | --- |
| 输出上下文路径 | 探查现实、澄清业务 |
| 校验章节、编号、关联、占位符和状态 | 从空正文构建契约块、Registry、规则和 AC |
| 执行状态迁移 | 检查单一事实来源和唯一解释，获取用户批准 |

CLI 不判断业务方案是否正确，也不替用户做产品决定。

## Stop Conditions

- Proposal 未 accepted 或范围变化 → 返回 `change`
- 一个 Change 包含多个独立系统 → 返回 `change` 拆分
- 需要改变 Blueprint 边界 → 暂停处理 Blueprint
- 业务规则仍有两种合理解释 → 询问用户
- 需要内部文件或技术方案决定 → 留给 `plan`
- 任何关键契约仍是“建议/或者/暂时” → 不 approved

## Handoff Rule

Spec approved（需要时 `diagrams.md` 已确认）→ `plan`。本技能不写 Plan、不修改代码。
