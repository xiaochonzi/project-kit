# Spec

## Overview

把 accepted Proposal 编译为**自包含、机器级确定、零歧义**的业务与领域设计契约，完整写入 `docs/changes/CR-###-<slug>/spec.md`。

Spec 回答“**系统对外呈现什么行为、具备哪些确定性数据契约与边界逻辑**”。它的唯一交付标准是：
> **任何没有原始对话上下文的执行 AI，仅凭落盘文档，即可 100% 确定地实现全部功能与验收测试；绝不需要在开发阶段自行脑补领域模型或猜测边界分支。**

- **Spec 锁死**：对外与核心领域数据 Schema（字段名、物理类型、枚举值、只读/可写、精度约束）、显式状态迁移表、全量协议与错误响应、多分支拓扑与决策矩阵。
- **Spec 解耦**：绝不规定内部类名、私有函数名、文件路径和代码修改步骤（这些属于 Plan 的工程职责）。

**开始前宣布：**“我正在使用 spec 技能设计业务契约。”

## The Iron Law

```
NO APPROVAL WHILE A SECOND REASONABLE INTERPRETATION EXISTS
```

1. **唯一解释铁律**：只要角色、输入、权威、状态、失败分支或验收标准仍存在第二种合理业务解释，就必须继续澄清。严禁把业务或契约决定推迟到 Plan 或编码阶段。
2. **自包含契约铁律**：严禁将目标模型定义、字段 Schema 或协议格式引用外部或前序 CR（例如写“沿用 CR-041”）。复用既有结构也必须就地给出完整的 Normative Schema 摘要。本文件必须是单一事实来源。
3. **拓扑结构化铁律**：凡涉及指针连接、图装配、多分支分叉与合流的复杂拓扑，严禁仅用纯文本叙述，必须提供 ASCII 拓扑图与决策矩阵表。

## 契约边界矩阵

| 架构必须绝对锁死的契约（严密定义） | 架构严禁越界规定的细节（解耦实现） |
|---|---|
| 业务角色、触发时机、前置条件、端到端业务流 | 内部类名、包名、私有函数名 |
| 对外及核心领域数据 Schema（字段名、类型、枚举、约束） | 具体文件路径和代码修改步骤 |
| 对外 API / 事件协议、参数定义、标准错误码与响应结构 | 内部调用链和模块分包实现细节 |
| 数据权威归属、业务状态集合、合法与非法转移矩阵 | DTO/VO 具体代码类名和任务拆分 |
| 复杂节点装配拓扑（ASCII 图）与条件决策矩阵表 | 具体第三方工具库选择与测试文件组织 |
| 权限、幂等、并发控制、异常边界防御与业务不变量 | 内部私有局部变量与临时算法缓存 |
| 可量化、输入输出确定闭环的 PASS / FAIL 验收标准 | 具体的代码行级修改指令 |

## Required Inputs

- [ ] `docs/changes/CR-###-<slug>/proposal.md` 存在且 `status: accepted`
- [ ] `docs/changes/CR-###-<slug>/spec.md` 存在且 `status: draft`（正文为最小骨架）
- [ ] 已完整掌握 Proposal 中的背景、EVD 证据、包含/不包含边界以及全部 DEC 冻结决定
- [ ] 当前 Change 是内聚、可独立交付与验收的业务闭环

Proposal 未 accepted → 返回 `change`。Spec 已 approved → 不重写，交接 `plan`。

## 核心契约法定大纲

Spec 从空正文生成时，**必须严格包含以下 12 个标准二级标题（`##`），文字必须精确匹配，严禁增加数字前缀（如 `## 1. 术语` 会导致门禁工具匹配失败，必须为 `## 术语与业务对象`），严禁合并或省略**：

```markdown
## 术语与业务对象
## 数据权威表
## 问题与依据
## 目标
## 用户流程
## 范围
### 包含
### 不包含
## 输入与输出
## 业务规则
## 失败与边界情况
## 禁止事项
## 验收标准
## 未决问题
```

## 核心契约编写规范

### 1. 术语与业务对象
确立领域词汇的唯一语义。每个概念、实体、对外 ID 必须有确定定义，杜绝同名异义与概念泛化。

### 2. 数据权威表
建立单一事实来源，用表格严密回答“该业务事实以谁为准”：
```markdown
| 业务事实 | 唯一权威来源 | 非权威来源不得做什么 |
|---|---|---|
| 订单实付金额 | 结算服务支付单 | 客户端/缓存不得自行计算或覆盖 |
```

### 3. 输入与输出（自包含 Normative Schema）
无论数据来自外部输入还是后端装配产出，**严禁仅使用自然语言或目录树总结**，必须提供机器可解析的代码级实体定义（TypeScript Interface 或 Java Class DTO）：
- 必须写明字段名、物理类型（如 `Long`、`BigDecimal`、`String`）、是否可空、枚举取值、数值保留小数位精度。
- 明确标注：
  - `Normative`：字段名、层级嵌套、数据类型属于硬性契约，实现必须严格一致。
  - `Illustrative`：仅为便于人类阅读的业务示意样例数据。

### 4. 复杂流转与装配拓扑（如适用）
涉及分支、合并、链表、指针跳转或状态机时，必须提供两件套：
1. **ASCII 拓扑示意图**：清晰展示节点派生、分支流向与汇聚出口。
2. **连接 / 状态转移决策矩阵表**：
```markdown
| 当前节点/条件 | 展开节点类型 | 内部边连接 (nextItemId) | 外部/出口边连接 |
|---|---|---|---|
| 条件 A | 节点 X | X.next -> Y.id | 指向后续集合首节点 |
```

### 5. 条件契约块（按需激活）
按需逐项明确以下适用块（不适用的明确写“不适用及原因”）：
- **状态迁移表**：合法起点 $\to$ 触发动作 $\to$ 目标状态 $\to$ 非法迁移拦截。
- **决策矩阵表**：条件组合 $\to$ 唯一确定结果。
- **全量错误字典**：业务错误码、触发条件、用户可见表现、HTTP/RPC 状态映射。
- **并发与幂等**：幂等键生成规则、重复请求返回策略、竞争冲突锁策略。
- **边界防御**：空值、非法边界、越权拦截、超时熔断、回滚策略。

### 6. 业务规则（BR-##）
聚焦于代码级业务不变量，编号使用 `BR-01`、`BR-02`...：
```markdown
- `BR-01`：<明确的单条业务规则或防御约束>
- `BR-02`：<明确的单条业务规则或防御约束>
```
**【统计/计算/查询特性 BR 必答清单】**：
- **除零防御（Zero-Division Defense）**：包含比率或平均值时，必须明确分母为 0 时的确定返回值（如 `0.00`），严禁抛除零异常或返回 NULL。
- **时区与窗口闭合（Time Window Invariants）**：统计时间必须指定业务时区（如 `Asia/Shanghai`），自然周/月/年必须明确起始点与截止点，统一换算为左闭右开区间 `[beginTime, endTime)`。
- **有效状态过滤（State Filters）**：凡涉及“有效数据”，必须写死具体的过滤条件（如 `del_flag = '0'`、`status != '0'`）。

### 7. 验收标准（AC-##）
- **禁止使用字母后缀变体（如 AC-01a）**。
- **可执行断言铁律**：严禁使用陈述句或业务口号。每条 AC 必须包含 GIVEN（前置数据与状态）+ WHEN（调用动作）+ THEN（精准结果断言），可由无上下文 AI 直接转写为自动化测试代码：
```markdown
- `AC-01`：GIVEN <明确前置状态/数据>，WHEN <调用接口/触发动作>，THEN <精准断言状态/返回值/副作用>
- `AC-02`：GIVEN <异常输入或边界条件>，WHEN <触发操作>，THEN <断言特定错误码与回滚表现>
```

### 8. 未决问题
提交用户批准前，必须消除所有未决问题，**精确填写为“无”**。

## Process

### Step 1：上下文加载与真实探查

```bash
node scripts/project-docs.cjs context spec --target <CR-###> --root <项目根>
```

探查现有代码契约、API 现状与系统行为，立足代码现实。

### Step 2：架构建模与消除歧义

逐一锁定：角色流程 $\to$ 权威归属 $\to$ 目标 Schema $\to$ 拓扑图与决策表 $\to$ 异常边界。遇到 2 种以上合理方案时，给出权衡并由用户裁决。

### Step 3：单一事实来源与自包含核查

核实每个事实在全文仅定义一次；核实核心数据模型全部就地自包含，不存在“参考外部 CR”等隐式依赖。

### Step 4：架构师自检

依据落盘的 `spec.md` 逐项确认：
1. 能否仅凭 Spec 为每条 AC 写出确定性的输入、执行与期望断言？
2. 目标数据结构是否完全自包含，无跨 CR 甩锅？
3. 复杂分支和指针是否有 ASCII 拓扑图与决策矩阵支持？
4. 是否未泄露内部实现细节（如内部类名、私有函数、文件路径）？
5. 是否已彻底消除第二种合理的业务解释？

### Step 5：用户批准与状态冻结

向用户展示架构契约摘要、关键 Schema、拓扑图与 AC 清单。用户明确批准后，通过 CLI 完成状态迁移：

```bash
node scripts/project-docs.cjs transition CR-### --to approved --kind spec --root <项目根>
```

**严禁在 markdown frontmatter 中手动编辑 `status: approved`！**

## Quality Checklist

- [ ] Proposal 处于 accepted，Spec 从空正文完整生成
- [ ] 12 个法定二级标题精确匹配且无数字前缀
- [ ] 术语定义无歧义，数据权威表覆盖全部核心业务事实
- [ ] 目标数据模型与 Schema 100% 自包含，无跨 CR 甩锅
- [ ] 复杂流转、多分支合流具备 ASCII 拓扑图与决策矩阵表
- [ ] 样例明确区分 Normative 契约与 Illustrative 示意
- [ ] 业务规则 BR 与验收用例 AC 编号完整，包含 GIVEN/WHEN/THEN，无字母后缀
- [ ] 无内部类名、私有函数、内部调用链或文件修改步骤
- [ ] 未决问题为“无”，用户明确批准并经 CLI 成功迁移至 approved

## Script / Author Responsibility

| CLI (`project-docs.cjs`) | 文档作者 (AI) |
| --- | --- |
| `context spec` 呈现只读上下文 | 建立领域模型、确立数据权威与 Schema 规范 |
| 机械门禁校验 12 个二级章节与占位符 | 绘制拓扑图与决策矩阵，消除业务歧义 |
| `transition ... --to approved --kind spec` 执行状态迁移 | 编写可直接转为测试的 GIVEN/WHEN/THEN 验收标准 |

## Stop Conditions

- Proposal 未 accepted 或范围发生变化 $\to$ 返回 `change`
- 目标数据模型未就地定义，仅引用外部/历史 CR $\to$ 补全 Schema 前禁止 approved
- 复杂网络逻辑未提供拓扑图或决策矩阵 $\to$ 补全前禁止 approved
- 业务行为存在第二种合理推论 $\to$ 暂停并向用户提问澄清

## Handoff Rule

Spec approved $\to$ `plan`。本技能专注架构契约设计，不编写 Plan，不修改代码。

## Anti-Patterns 负面清单

1. **严禁手动篡改 status 为 approved**：创建后必须保持 `status: draft`，严禁由模型手动在 frontmatter 中改为 `ready` 或 `approved`；必须由用户确认后通过 CLI 迁移。
2. **严禁二级标题加数字前缀**：严禁写成 `## 1. 术语与业务对象`，必须直接写为 `## 术语与业务对象`，否则门禁脚本正则提取将判定为空章节。
3. **严禁使用 ASCII 树或自然语言替代数据结构**：必须给出显式的 TypeScript Interface 或 Java Class DTO 代码。
4. **严禁验收标准写业务愿望**：严禁写“验证任务不双重统计”等无断言陈述句，必须包含 GIVEN/WHEN/THEN。
