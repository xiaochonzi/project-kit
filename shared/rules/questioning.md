# 澄清与设计对话

## 一次只解决一个决策

每轮只提出一个最影响下一步的问题。优先使用 2–3 个互斥选项，给出推荐项和取舍；确实无法枚举时才使用开放问题。不要一次抛出问题清单让用户替 AI 做信息整理。

## 问题优先级

依次处理：

1. 会改变项目目标或用户结果的问题。
2. 会改变系统边界、数据权威或外部依赖的问题。
3. 会改变安全、合规或不可逆数据行为的问题。
4. 会改变验收方式的问题。
5. 仅影响实现偏好的问题；此类通常推迟到 Plan。

## 五个检查视角

- 研究者：哪些外部事实、既有代码或用户行为尚未确认？
- 简化者：最小能产生完整价值的边界是什么？
- 边界守门人：明确不做什么，谁拥有数据与职责？
- 失败分析者：失败、重试、权限、离线、并发和数据损坏时发生什么？
- 收口者：哪些遗留问题会在以后推翻当前设计？

## 方案呈现

对存在实质分歧的设计给出：

1. 推荐方案。
2. 最多两个合理替代方案。
3. 每个方案的用户影响、复杂度、风险和可逆性。
4. 需要用户决定的单一问题。

## 分节批准

大型 Blueprint 或 Spec 不应一次性倾倒。按“目标与边界 → 能力与流程 → 数据与模块 → 失败与非功能 → 路线与验收”分节呈现；每节确认后再继续。用户提出修改时，更新该节并检查对后续已确认部分的连锁影响。

## 禁止

- 不问能从仓库、原文或现有文档直接查到的问题。
- 不把技术偏好伪装成产品必答题。
- 不用“是否还有其他要求”代替针对性收口。
- 不在关键答案缺失时自行填补并继续计划。
