# Constitution Workflow

## 目的

制定跨功能、跨阶段都稳定适用的开发准则，作为后续拆解、计划、实现与验收的最高项目约束。

## 必读

- 仓库规则与现有架构文档。
- `../templates/constitution.md`。
- `../rules/clarity-gates.md`。

## 流程

1. 收集已有的产品、架构、数据、安全、质量、测试、依赖和文档规则。
2. 去除只影响单一功能或当前迭代的内容；这些内容应进入 Spec 或 ADR。
3. 标记规则冲突、重复和缺失。
4. 每次只提出一个会显著改变规则的问题，并说明为什么必须现在决定。
5. 为存在合理分歧的问题给出 2–3 个选项、推荐项和取舍。
6. 按模板逐节起草；每节保持可执行、可检查，避免价值口号。
7. 请用户审阅原则及禁止事项。
8. 批准后写入 `docs/constitution.md`，更新版本、日期和修订记录。

## 门禁

- 每条原则必须能影响设计、实现或验收决定。
- 原则之间不得矛盾。
- 禁止事项必须明确边界，不能用“尽量”“适当”等不可验证措辞。
- 不把当前库版本、临时排期或单功能需求写成宪章。

## 状态更新

在 `docs/STATE.md` 的 Decisions 中记录 Constitution 已批准及其版本。

## 停止条件

- 项目关键架构方向尚未确定且会导致完全不同的准则。
- 新准则与仓库强制规则冲突。

## 成功标准

- 用户明确批准。
- 后续 Feature 与 Plan 可以逐条检查是否合规。
