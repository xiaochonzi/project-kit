# Bug Workflow

## 目的

系统定位并直接修复违反已有预期的缺陷，留下可追溯的根因与回归证据；不创建 Implementation Plan。

## 必读

- `../rules/debugging-rules.md`
- `../rules/verification-rules.md`
- 相关 Feature Specs、Bug 现场、日志、测试和代码路径。

## 流程

1. 收集实际行为、期望行为、最小复现、环境和首次出现时间。
2. 找到被违反的 Spec 验收标准。若找不到且用户要求的是新行为，停止并转 `change`。
3. 稳定复现；不能复现时收集边界证据，不猜测修复。
4. 沿数据和控制流从症状追到最早错误状态，区分根因与连带症状。
5. 对照同仓库可工作的相似路径，列出关键差异。
6. 提出一个可证伪的根因假设，并用最小实验验证。
7. 按仓库门禁说明最小修复方案并取得授权；执行要求的影响分析。
8. 先添加或确认能失败的回归测试，再做一个针对根因的最小修复。
9. 运行回归测试、相关测试和必要构建，检查没有引入未批准行为。
10. 若一次修复失败，回到证据；不要叠加猜测性改动。三次独立修复均失败时，停止并质疑架构或问题定义。
11. 使用 `new fix` 创建 Bug Resolution，记录现象、复现、被违反 Spec、根因、修改文件和新鲜验证结果。
12. 更新 STATE 的 Blockers/Recent Results；不要为 Bug 创建 Plan。

## 停止条件

- 无法证明它违反已有行为。
- 无法稳定复现且缺乏足够证据。
- 修复需要扩大产品范围、数据迁移或新架构决定。
- 三次失败的修复尝试表明问题模型错误。

## 成功标准

- 根因而非症状被修复。
- 回归测试在修复前失败、修复后通过。
- Bug Resolution 能让他人复现问题与验证修复。
